# Reproduction guide

This guide documents the model reports, fixed frame selections and scoring code behind the paper. Run all commands from the repository root. [Repository overview](../README.md) · [Paper (PDF)](../paper/manuscript.pdf)

The original MLVU development study covers 206 questions. Its historical four-seed comparison uses the 200 questions with reports in both sampling conditions. The matched fourth-call study uses independently acquired uniform and change-selected fourth inputs. Each subsequent study records its cohort and required responses separately.

The published-model panel in Table 2 quotes task accuracies from six formally published systems. The [transcribed scores](../published_baselines/reported_results.csv) and [original table locations](../published_baselines/sources.json) identify the development or test split, backbone and input protocol for each result. Vgent uses audio transcripts, HPP combines planning and perception models, and DIG uses 192 selected frames with its 32B backbone. Blank CSV test fields denote an unreported test score in the cited source. [Published comparison notes](../published_baselines/README.md).

## Run the offline analysis

Use Python 3.11 or later with NumPy and scikit-learn. The verification environment used Python 3.13.5, NumPy 2.5.4 and scikit-learn 1.7.2. The analysis reads the bundled CSVs and runs on CPU without credentials, internet access, model weights or videos. To install missing dependencies and write the full result, run the following commands from the repository root.

```sh
python -m pip install -r requirements.txt
python reproduce.py --out metrics.json
python -B verify_all.py
```

`verify_all.py` checks the SHA-256 manifest, replays the numerical studies, compares the resulting files with the archived results and verifies the stopping rule on every legal continuation. It writes working files to a temporary directory.

Without `--out`, `reproduce.py` prints its results as JSON. It searches the original parameter grid using the development half, runs the selected scorer on every row, and checks all 206 predictions against the archived MAMC outputs. A disagreement raises an error. To check the files against the release manifest, run `shasum -a 256 -c SHA256SUMS` (macOS) or `sha256sum -c SHA256SUMS` (Linux). The archived output column serves only as a check. For original file digests and model configurations, see [source checksums](../data/source_checksums.json) and [run settings](../data/runs.json).

The held-out table gives MAE 0.427 versus 0.301 and residual undercounts and overcounts of 16 and five.

### Historical answer extraction

Of the 824 historical report prefixes, 121 contain no digit and 113 of those calls reached the output-token limit. These prefixes occur on 80 questions, accounting for nine of the eleven net additional correct answers under the original floating-point implementation. On the other 126 questions all four stored prefixes are legal numerical options that match the archived reports. The four-call estimator answers 111 correctly and the first call 109. ### Reading the JSON output

The named field `matched_development_table` reports correct counts, MAE and paired wins and losses against the first uniform call for the original 103 held-out items and the complete 206-item development set. It supplies the development comparisons in manuscript Table 2. MAMC uses a score based on the magnitude of each count discrepancy and the number of matching reports.

- `selection` gives the fitted parameters and the matched 103-question holdout comparisons. The full-set accuracy includes the 103 tuning questions. The selection maximizes dev accuracy across the grid in the code and uses the first grid entry on a tie. Splitting sorts the original filenames lexically before applying NumPy's default generator, seed 0.
- `ablations` reconstructs all eleven settings. For the rounded median, half-integer medians go to the nearest even integer. A majority-vote tie goes to the first tied count in the original input order. The four inputs, in order, correspond to the archive labels uniform, random, recency and change. The first three actually retained the entire uniform pool. At 64 and 32 frames a single uniform call has 92/148 and 39/138 correct. The matched four-call results are 109/148 (73.64865%) and 101/138 (73.18841%).
- `tie_sensitivity` gives the 18 tied items, their valid score maximizers and their archived decisions. The original coefficients are (0.8, 0.8, 0.4). The script sums binary64 contributions left to right, preserving the archived operation order across Python versions. Under integer coefficients (2, 2, 1), all mathematically equal scores tie exactly. Selecting the smallest tied count changes 12 outputs from their archived decisions. The finite candidate set for the aggregate is 1 through 5. Individual calls chose among the four numbers supplied with each question, which can include 0 and 6.
- `strata`, `errors` and `agreement` give exact counts by true answer and by video duration, the single-to-aggregate error transitions, and between-call agreement. The shorter group contains 170 videos and the group at least 600 s long contains 36. This replay uses the public annotation durations. Both groups reproduce the published correct totals (129 to 136 and 19 to 23 respectively). Signed-error labels describe only the numerical direction.
- `sampling_control` uses matched inputs and the same estimator and reports each run's individual accuracy, agreement, and gain over the strongest single call. `figure_data.sampling_control` returns the source percentages for the best single/aggregate comparison: 73.5/78.5 (primary), 64.0/67.0 (seeded). The legacy `figure_data.count_errors` retains the full-development record: 18 corrections, 7 newly wrong answers, and under/overcounts of 40/18 before aggregation and 37/10 after. Current Figure 3 uses `figure_counts` in [held_out_errors/results.json](../held_out_errors/results.json), with 8 corrections, 5 introduced errors, 16 residual undercounts and 5 overcounts.
- `duration_audit` recomputes the depth-three tree using stratified five-fold validation, a shuffled split with random state 0, and the same fixed seed for the tree. The equally weighted fold mean is 61.66086%; pooling its out-of-fold predictions gives 127/206. The in-sample majority label of each nearest-second bin gives 194/206 (94.17%) across 82 distinct bins. Two historical auxiliary estimates, 69.7% for a count-based classifier and 79.3% for a duration-aware calibrator, lack matched item outputs and a confirmed denominator. The reproducible estimates in this release use item-level predictions.
- `reasoning_count` compares four reasoning-enabled calls against one reasoning-disabled call and gives the single uniform call in each setting. `cross_task` uses paired numeric option indices for 237 event-order and 329 needle-localization questions. Each of these two tasks uses one call per condition. The enabled prompt also asks the model to think carefully. Unlike the counting run summaries, these two tasks' archives do not store the requested model identifier.
- `inference_cost_estimates` extrapolates from the first uniform call. Historical rates are USD 0.28 per million prompt tokens and USD 0.42 per million completion tokens. The model for ideal parallel time assumes all four calls have the single-call latency. Multiplying the measured mean 8.54792 s by four gives 34.19169 s; multiplying its displayed 8.5 s by four gives 34.0 s. The archive has no measurement of joint wall-clock latency.

For small numbers of discordant pairs (up to 25), the paired test is exact. Above 25 the script uses the original continuity-corrected chi-square approximation. Bootstrap calculations use 10,000 draws over questions with seed zero. The paired bootstrap reports twice the fraction of sampled accuracy differences at or below zero for the observed positive effect. Zero such draws is a finite simulation outcome. The report expresses accuracy in percent and paired differences in percentage points. Bootstrap interval endpoints in the JSON are proportions. The exact net accuracy gain is 11/206, or 5.3 percentage points to one decimal place. The undercount and overcount rates fall by 1.5 and 3.9 points respectively, and the five-occurrence group loses 1/39, or 2.6 points.

## Records and provenance

- [Counting observations](../data/action_count.csv) preserves public annotation order. The ID is the public MLVU video basename without its extension. It carries the numeric gold answer, duration in seconds, seven primary or ablation outputs, four seed outputs, the archived aggregate, and three per-question usage measurements from the first uniform call. A blank cell means an unavailable run output. All other predictions are parsed numeric answers. The run configurations record the actual candidate-pool size.
- [Reasoning observations](../data/reasoning.csv) uses a task ID and the **one-based row number** in the corresponding public MLVU development annotation. Gold and predicted options are **zero-based indices**. The source pairs were joined on the original video ID and question. Null parsed answers are blank and count as incorrect.
- [Source checksums](../data/source_checksums.json) identifies the input annotation snapshots, archived run files, metric summaries and original implementations by relative filename and SHA-256. The data files contain numeric derivatives and public item identifiers. The package omits videos, free-text generations and access credentials. ## Reconstruct counting inputs and parsing

[inference_protocol.py](../inference_protocol.py) reconstructs the archived counting driver's default number-choice prompt, pool sampling, view selection, JPEG encoding and answer parser. For a requested public counting video it prints the selected source-frame indices. Running this optional step with video decoding needs OpenCV and Pillow. It writes a request body only when explicitly asked. An optional single-item inference mode accepts a user-configured endpoint.

```sh
python inference_protocol.py --run full206_change --item count_0 \
  --annotations /path/to/4_count.json --video /path/to/count_0.mp4
```

For a new inference request, set `MAMC_API_URL` to your full HTTPS chat-completions endpoint, set `MAMC_API_KEY` in your environment, and add `--submit` to the example. This sends the supplied question, numeric options and selected image frames to that endpoint. It prints only the item ID and parsed count. The endpoint must accept the archived model alias, image inputs, and the thinking request field. One invocation makes at most one request. HTTP redirects are disabled. To freeze Python's hash salt for new random samples, set `PYTHONHASHSEED=0` before launching each Python process and retain the same explicit seed and software versions.

The optional `--write-request payload.json` serializes the reconstructed request including base64-encoded video frames. With `--read-response response.json` the script also parses a caller-supplied response locally. The original parser scans the first integer of the final content, falling back to reasoning content if the final content is empty, then maps that integer to the nearest offered option (earliest offered option for an equal distance). The per-call source records contain at most a short response prefix, and the package includes only the parsed numeric choice. These records reproduce the scores. Full verification of every historical extraction would require the complete model answers.

The counting client requested the alias `deepseek-flash` with the temperature field set to zero. The provider documents that thinking mode accepts this field for compatibility and ignores its value. Replaying the same reasoning-enabled request therefore fixes the client input and leaves decoding under service control. [DeepSeek thinking-mode parameters](https://api-docs.deepseek.com/guides/thinking_mode/#input-and-output-parameters). The four primary calls and the four seeded calls used the reasoning-enabled request with an 8,192-token cap. The uniform reasoning-disabled comparison used a 64-token cap. The historical archive lacks the server revision, request IDs and per-frame source indices for those calls. The random subset generator incorporated Python's process-salted hash of the pool size in addition to the explicit seed (1 through 4). The original hash salts are unavailable. The supplied reconstruction implements the sampling algorithm. Matching the historical draws would also require the original process salts. The 200-item matched comparison uses their saved numerical outputs.

## Paired fourth-call frame-selection experiment

The two arms reuse the same three archived uniform-frame reports and differ only in the input to a newly acquired fourth call. Arm A uses uniform frames. Arm B uses frames selected for visual change. The new calls requested the same model alias, prompt, temperature, reasoning setting and output limit in both arms. Historical upstream reports used the original answer parser. For the fourth call, an accepted response consists of one of the four options in the final answer after trimming whitespace. Blank or unsupported answers have explicit statuses.

The planned cohort contains 206 questions. Both arms have terminal records for every planned question. On the original 103-question held-out half, 80 questions have two usable fourth-call answers. The analysis records coverage separately for each arm, reports matched estimates, and gives bounds for the primary accuracy difference across the entire planned cohort.

The [analysis plan](../fourth_call/protocol.md) was fixed before inspecting the new calls. The [run settings](../fourth_call/run_settings.json) record the model alias, acquisition dates and output criteria. The [terminal counts](../fourth_call/terminal_counts.jsonl) and [selected frame indices](../fourth_call/selected_frames.jsonl) are keyed by benchmark ID and arm. The [item table](../fourth_call/paired_items.csv) lists each question's original split, reference count, arm statuses, fourth reports and primary predictions. The [paired results](../fourth_call/results.json) and item table are reproducible with the following command from the repository root.

```sh
python fourth_call/analyze.py fourth_call/terminal_counts.jsonl --archived-csv data/action_count.csv --annotations fourth_call/options.json --scope all --out replay.json --items-out replay_items.csv
```

In the replay, `historical_fourth_holdout_103` reports the first uniform call, the shared three-call aggregate and the scoring rules applied to the original fourth report on the same held-out items. `primary_103` uses the newly collected fourth calls.

During data collection, the [acquisition notes](../fourth_call/acquisition_notes.md) recorded the retry policy introduced after a network failure. Each arm accepts the first complete model response, including a blank or unsupported answer. Transport and transient HTTP failures can replay the identical payload for up to five total client attempts. The status table includes terminal HTTP errors, exhausted retries and unrecorded arm slots where applicable.

An additional sensitivity analysis enumerates the four offered answers for each missing slot. Its bounds apply to a hypothetical valid completion, preserving the three archived reports and the fixed smallest-maximizer rule. The results include these conditional-assumption bounds alongside the original unconstrained bounds.

For an individual input, supply the original MLVU Action Count dev annotation and video directories. The [public video source manifest](../fourth_call/video_sources.json) gives the dataset revision, mirror revision, sizes and SHA-256 digests for seven videos retrieved during this run. The commands below rebuild the uniform and change-selected requests offline and check their bytes against the stored SHA-256 digests. Install OpenCV and Pillow for these optional calls. Set `MLVU_ANNOTATIONS` to the public `4_count.json` and `MLVU_VIDEOS` to the directory containing the counting MP4 files.

```sh
python fourth_call/replay_call.py --annotations "$MLVU_ANNOTATIONS" --video-dir "$MLVU_VIDEOS" --item count_0 --arm uniform --write-request uniform_request.json
python fourth_call/replay_call.py --annotations "$MLVU_ANNOTATIONS" --video-dir "$MLVU_VIDEOS" --item count_0 --arm change --write-request change_request.json
python fourth_call/replay_call.py --annotations "$MLVU_ANNOTATIONS" --item count_0 --arm uniform --read-response saved_response.json
```

To independently recalculate the frame selection itself, use the top-level `inference_protocol.py` with `--run full206_uniform` or `--run full206_change`, the same public video, and `--write-request`. The saved-response example above reproduces the stricter final-answer parser applied to these new fourth calls.

For a fresh paired run, the [acquisition script](../fourth_call/collect.py) implements the study's collection order, image selection, provider requests, retry handling and strict final parser. Its public version takes the video and annotation paths on the command line. Install requests, NumPy, OpenCV and Pillow on a Unix-like system and set `MAMC_API_KEY` in the environment. The command below sends up to two paid model calls per question before transport retries. `--scope holdout` selects the original held-out half. `--scope all` selects both halves, starting with the holdout. The run directory records source-frame indices, final text, usage and provider request identifiers for local audit.

```sh
python fourth_call/collect.py --annotations "$MLVU_ANNOTATIONS" --video-dir "$MLVU_VIDEOS" --scope holdout --jobs 3 --run-dir local_run
```
